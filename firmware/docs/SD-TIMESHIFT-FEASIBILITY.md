# SD time-shift — реализуемость и барьеры

**Статус на 10 ноября 2026:** immutable-релиз Pocket Jazz **v0.7c успешно собран и проверен на ПК** (99 Python / 16 C++ Release, Arduino compile), но **не содержит рабочего PAUSE / −30 / LIVE с записью на SD**; на устройстве он не проверялся и **NOT CLEARED FOR INSTALL** до PMan. Отдельный Audio Router SDK **v0.8b-host-only** теперь опубликован с исправленным свежим source-bound gate: **MSVC Release 19/19**, Arduino ESP32-S3 compile-only PASS, 47 проверенных исходников вместе с MIT LICENSE, source ZIP SHA-256 `320b5cbb09bef7cf0daca7dae9b4503c25a9b44d38f31c3c701e29416c46c9af`. Исторический `0.8a-host-only` не менялся. Все MP3 time-shift компоненты остаются **host-only**, не подключены к настоящему SD worker, HTTPS/HTTP-клиенту или декодеру.

**Обновление после отдельного SDK-релиза:** `audio-router-sdk/dist/releases/0.8c-host-only` уже выпущен (fresh **20/20 CTest**, ESP32 compile-only, 50 source SHA, MIT LICENSE, ZIP SHA256 `b25ed2131aa6451f59c727b250fcc372cc2ed9a6a571807fc87c44731d6e516c`). Добавлен прототип `PreallocatedPjmfSdRing`: вызовы `readAt/writeAt/flush` к внешнему блочному файлу с заранее выделенными слотами по **1504 Б**, проверки точных length/epoch/sequence/CRC/overwrite и bounded draining из FIFO. **Не является настоящим SD driver**: ни FATFS, ни гарантий flush при потере питания, ни аудиовывода на ADV. Arduino compile-only v0.8c проверяет общий SDK, но не инстанцирует новый SD-ring-класс; потребуется явная отдельная ESP32-проба в следующем этапе.

**SDK v0.8f-host-only (новейший отдельный SDK archive, не app firmware):** immutable ZIP SHA256 `015f1f330185159e9583f28466ffdfd549217051a51da735af4d42f3766affbf`, **22/22 MSVC Release**, ESP32-S3 compile-only, 56 source SHA и MIT LICENSE. `ArduinoPjmfFileAdapter.h` обеспечивает проверенный на host контракт с **внешним уже открытым** `fs::File`: `seek(uint32_t)`, точный 1504-byte read/write, предварительный размер ≥slots×1504, ограничения uint32, защита от ejection/short I/O, sticky fault. Не вызывает `SD.begin`, `File.open`, форматирование, изменение размера или фоновые файловые операции. `fs::File::flush()` в core 3.3.9 возвращает **void**, поэтому для подтверждения долговечности нужна отдельно проверенная callback-политика; без неё adapter `flush()` отказывает. Host тест не доказывает, что SD данные переживут потерю питания; нет настоящей карты, двухстороннего ring-worker, HTTP/decoder и time-shift клавиш на ADV.

## Существующие варианты

1. **Байтовое кольцо** `experiments/TimeShiftRing.h`: абстрактный предвыделенный random-access носитель, 64-битные смещения, wrap, детекция перезаписи истории и отказ при ошибках чтения/записи. Смещения в байтах **не означают секунды** и не гарантируют границу MP3-фрейма.
2. **PCM16 record** `../../../audio-router-sdk/prototypes/sd_timeshift/Pcm16RingRecord.h` (путь от папки `docs/`): `PJTS` v1 — 1056 байт на слот, 32-byte header + 1024 байта (256 interleaved stereo PCM16 frames), sequence, sample rate, valid frames, CRC32. Ничего не сохраняет на SD. Для 44,1 кГц stereo 16-bit исходный PCM ≈176,4 кБ/с без записи заголовков; велика нагрузка и износ SD.
3. **Compressed MP3 frame record/index** `Mp3FrameFormat.h`, `Mp3FrameRingIndex.h` и `MP3-TIMESHIFT-PROTOTYPE.md` в том же SDK: синтаксически проверяет **целый** MPEG-1/2/2.5 Layer III frame после удаления ICY, сохраняет в `PJMF` v1 слот ровно **1504 байта** (32-byte header + до 1441 frame bytes + zero padding); sequence, epoch, CRC32, проверка формата и `main_data_begin`. `seekBack30Seconds` использует decoded samples (не CBR byte offset), выбирает reservoir-independent preroll anchor и требует **не менее 12 полных preroll-фреймов** и сохранности всего диапазона. Возвращает `SeekPlan` с `skipSamples`, **не** звуковой результат. Реальный decoder может нуждаться в дополнительном preroll; проверка заголовка не доказывает декодируемость payload; MPEG CRC16 не проверяется.

**Что в SDK уже есть (только host-only):** `IcyMp3Stream.h` содержит `IcyAudioStripper` — incremental удаление ICY metadata из **HTTP entity-body** при известном и отдельно проверенном `icy-metaint`, с обработкой разделённых по сетевым chunk метаблоков. `Mp3StreamFrameAssembler` собирает полные Layer III frames из фрагментов входа, требует подтверждение следующей frame boundary и сигнализирует loss-of-sync. `Mp3CaptureProducer.h` объединяет stripper → assembler → `PJMF` encode → `Mp3SlotFifo.h` (фиксированный bounded SPSC FIFO); `Mp3TimeShiftSession.h` моделирует GAP/LIVE/PAUSED/DELAYED и seek на host. **Это не готовая интеграция HTTP chunked transfer framing, TLS, SD, decoder или радио.** Парсер должен получать именно entity-body после снятия transfer encoding и строго проверенного HTTP/ICY заголовка; некорректное `icy-metaint`, network loss, FIFO overflow и повреждение метаданных создают discontinuity. Синтетические host-fixtures не доказывают реальную аудиодекодируемость.

## Оценка памяти и SD-трафика

| Хранение | 30 с | 60 с | 5 мин |
| --- | ---: | ---: | ---: |
| Плотный MP3 @128 кбит/с | 480 000 Б | 960 000 Б | 4,8 МБ |
| `PJMF` @44,1 кГц MPEG-1 (≈38,28 слота/с × 1504 Б) | ≈1,73 МБ | ≈3,45 МБ | ≈17,3 МБ |

Фиксированная запись делает адресацию `(sequence % slots) * 1504` постоянной, но тратит ≈57,6 кБ/с вне зависимости от VBR битрейта. **Старый** `Mp3FrameRingIndex<2048>` в MSVC x64 host занимал **114 744 B**. Проверенный в **immutable SDK v0.8b host gate** компактный индекс `<2048>` занимает **24 632 B**, сессия **24 680 B** (экономия индекса **90 112 B / 78,5%**). Сессия `<3072>` — **36 968 B**, меньше ориентировочных 40 KiB. Это **не ESP32 runtime heap/stack измерения**, и `sizeof` сам по себе не доказывает реализуемость на плате без PSRAM. 2048 записей — номинально ≈53,5 с при MPEG-1 44,1 кГц, но реальная −30 с история требует >=12 preroll frames, независимую reservoir anchor, непрерывность, SD slots и CRC; произвольный VBR, медленная SD и питание могут уменьшить полезное окно. Подробнее — SDK `prototypes/sd_timeshift/COMPACT-MP3-INDEX-v08b.md`. FIFO существует в host-коде, но отдельный SD worker, backpressure при real latency и сериализация SD с UI/плейлистами пока не реализованы. Писать SD в аудио-callback нельзя.

## Правила PAUSE / −30 / LIVE, которые ещё нужно реализовать

- **PAUSE:** остановить выдачу пользователю, а не предполагать, что сервер остановил поток. Продолжать временный cache только после отдельного opt-in, при наличии SD и ограниченного объёма. Старые сохранённые записи могут перезаписываться кольцом.
- **−30:** переход только на подтверждённый последовательный MP3 frame, с обнулением/прогревом decoder от безопасного preroll anchor и отбрасыванием `skipSamples`; если недостаточно истории или frame chain повреждён, отказ с понятным состоянием, а не произвольный seek.
- **LIVE:** переход к фактическому текущему live, reset буферов и decoder. Пропущенные во время offline аудиобайты сервер обычно не восполняет. Ни одна реализация не должна «создавать» пропущенную музыку; discontinuity/gap запрещает перемотку через разрыв.
- Любая смена станции, сбой/разрыв TLS, неверный ICY interval, недозаписанный слот, SD stall/ejection, format change и неизвестная непрерывность должны менять continuity epoch. Записанный слот нужно проверить снова непосредственно перед воспроизведением; seek plan становится недействителен после overwrite или gap.
- Вещательские условия и местное право могут ограничивать запись эфира. Временный cache — только отдельный opt-in, лимитированный preallocated файл, без перезаписи Likes/плейлистов, без несанкционированного архивирования и без обещаний secure deletion на NAND.

## Аппаратные критерии допуска

Сначала проверка настоящих CBR/VBR MP3 + ICY metadata с разорванными на chunks заголовками и metadata blocks, реальный decoder preroll/seek, ошибки CRC/sequence и continuity. Затем 30–60-секундный буфер на Cardputer ADV, SD read/write p95/p99 stalls, heap/stack, Wi-Fi/HTTPS underruns, остановка/возобновление, частичное питание и физическое извлечение SD, ≥1 час непрерывного воспроизведения и откат через M5Launcher. До этого **никакого заявления о готовности SD time-shift**.

**Проверка в этом проходе:** только чтение исходников/документов SDK, официально опубликованного манифеста и отчётов v0.7c. Сам v0.7c archive уже был собран в независимом предыдущем проходе; **здесь** не выполнялись компиляция, SDK gate, прошивка, запись на SD или release packaging. Пока не закрыты вопросы лицензирования/устаревшего gate текущей SDK и нет аппаратных измерений, **не обещать SD time-shift**.
