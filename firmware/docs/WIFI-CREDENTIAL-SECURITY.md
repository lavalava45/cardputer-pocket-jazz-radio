# Wi-Fi credentials: безопасная миграция и границы защиты

**Состояние на 12.11.2026:** подготовлена только тестируемая host-side логика миграции, **шифрование Wi-Fi-паролей на Cardputer ещё НЕ включено**. Никаких eFuse, NVS, flash/разделов или прошивки устройства эта работа не затронула. Ни новый защищённый backend, ни источники ключей в production не подключены.

## Обнаруженное состояние

- Установленный в проекте Arduino-ESP32/m5stack core **3.3.9**: `CONFIG_NVS_ENCRYPTION`, `CONFIG_FLASH_ENCRYPTION_ENABLED` и `CONFIG_SECURE_FLASH_ENC_ENABLED` **не включены** по локальному `tools/esp32s3-libs/3.3.9/sdkconfig`. Это сведения **о собранном SDK**, а не о eFuse физического ADV. Ни наличие пользовательского аппаратного HMAC-ключа, ни статус flash encryption/eFuse на реальном устройстве чтением пока не установлены.
- В `PocketJazzRadioApp.cpp` сейчас сохраняются **незашифрованные** `Preferences.putString(...)`: `w00p/w01p` и `w10p/w11p` (оба банка по два профиля) плюс совместимый со старой прошивкой singleton `pass`; SSID: `w00s/w01s/w10s/w11s` и `ssid`. Коммит текущего формата — `wfcv=1`, `wfa` (последний marker), `wflast`. Текущая версия не имеет безопасного автоматического способа мигрировать эти записи без изменения схемы хранения.
- `WiFi.persistent(false)` не даёт Wi-Fi-драйверу дополнительно сохранять свои профили; маска в интерфейсе, исключение паролей из SD backup и отсутствие логирования **не защищают** уже записанный NVS от чтения flash.
- Знание MAC, chip ID, firmware BIN или пользовательского SSID **не является секретным ключом**. XOR, Base64, константа в исходниках или AES с ключом, выводимым только из этих доступных данных, запрещены как имитация защиты.

## Что реализовано только для host-тестов

Файл `PocketJazzRadio/WifiCredentialMigration.h` — независимый от Arduino C++11 policy-координатор для будущего **аппаратно защищённого аутентифицированного** хранилища, которое должно предоставить backend (`hardwareProtected`, `stageEncrypted`, `readStaged`, `commitStaged`, `readCommitted`, `purgeLegacyPlaintext`).

1. Отказ при недоступном защищённом ключе; никаких «зашифрованных» записей со слабым заменителем ключа.
2. Валидация обоих профилей и выбранного active, запись в неактивную защищённую область, **побайтовая проверка смысловых полей после чтения/аутентификации**, только затем коммит активной записи.
3. Если коммит-маркер защищённой схемы уже существует, ошибка чтения/аутентификации даёт `SecureUnreadable`, а не неявный откат на `pass`. В том числе при неопределённости после прерывания питания сразу после записи маркера.
4. Старые plaintext-ключи не очищаются на этапе записи. Только после отдельного **холодного запуска**, доказанного backend событием `recoveredOnColdBoot()` (нельзя выставить сразу после записи в том же сеансе), восстановления обоих профилей из protected store, успешной Wi-Fi-ассоциации и явного разрешения на очистку можно попросить backend удалить **оба старых банка + `pass`**.
5. Удаление NVS-ключей **не доказывает физическое стирание прежних байтов** из flash (wear levelling, оставшиеся страницы, резервные копии, старые дампы). Реальная гарантия отсутствия остаточных открытых копий требует продуманной процедуры provision/flash, с сохранением пользовательских данных и отдельным согласием.

Новый тест `tests/wifi_credential_migration_test.cpp` (зарегистрирован в `tests/pcm/CMakeLists.txt`) покрывает два профиля, открытую сеть, отсутствие ключа, неверный профиль, сбои staging/readback/commit, имитацию частично выполненного commit, cold reboot, требование работающего подключения, отказ при повреждении encrypted record, отсутствие скрытого plaintext downgrade и очистку legacy только по явному разрешению. **MSVC x64 Release host CTest: 2/2 теста Wi-Fi PASS**, включая предыдущий тест политики профилей. ESP32-компиляция, Arduino NVS integration, power-cut hardware, дамп flash и реальный reboot не проверялись.

## Что осталось для настоящей защиты и почему это отдельный этап

1. **Read-only hardware audit:** установить на конкретном ADV статус eFuse/flash encryption/HMAC средствами, не меняющими устройство, и реальную partition table. Не использовать настройки PC-SDK вместо сведений о физическом чипе.
2. **Выбрать полноценный root of trust и storage backend:** аппаратно связанный секрет (например, поддерживаемый SDK eFuse HMAC scheme или эквивалент), подтверждённый способ генерации/восстановления NVS encryption keys, authenticated NVS, boot order и размер требуемых partitions. *Просто создать NVS key partition с открытым ключом без flash encryption — не защита от offline-дампа.* Не вводить собственную криптосхему без необходимости.
3. **Полностью реализовать SecureStore в Arduino:** допустить запись только при аппаратной аттестации, обеспечить подлинность/целостность и независимый secure commit marker, подключить `restorePrefs()` и `commitWifiProfiles()` к новой схеме **без совместимой plaintext-копии**, а не только к helper-классу. Запретить старым веткам `saveWifi`, Wi-Fi migration и NVS rollback восстанавливать `pass`/банки после миграции. Переход с `wfcv=1` на новый номер схемы спроектировать так, чтобы старый BIN не мог незаметно перезаписать защищённые данные.
4. **Тестирование:** два профиля после холодного запуска; ошибки чтения/подменённый GCM tag; миграция и power cut перед/после каждого шага; сетевое подтверждение; отсутствие паролей в SD/Serial/TSV; анализ контролируемого flash-дампа на plaintext и отдельно документирование старых физических остатков.
5. **Только по отдельному явному разрешению**: provisioning eFuse, включение flash/NVS encryption, запись новых partitions, применение миграции к NVS или прошивка самого ADV. До этого **действующее поведение Wi-Fi и plaintext NVS не меняется**; ни автоматической очистки, ни иллюзии защиты нет.

**Почему не включён программный AES сейчас:** автоматическое восстановление двух сетей после cold reboot требует восстановимого ключа. Если ключ/пароль для расшифровки находится в том же читаемом BIN/NVS, офлайн-атакующий восстановит пароль; если ключ вводить вручную при каждом запуске, меняется требуемое поведение автоматического Wi-Fi. Для пользователя приемлемый выбор пока не согласован; реализован только безопасный, тестируемый механизм перехода.
