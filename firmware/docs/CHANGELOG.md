## После v0.7z3 — ограничение удержания MP3 RAM при TLS reconnect (12.11.2026)

**Экспериментальное исправление в рабочем дереве, без опубликованного нового BIN и без аппаратной проверки.** На физическом Cardputer ADV пользователь сообщает, что после длительного `RETRYING` Swiss Jazz больше не заиграла ни одна станция. Для Swiss Jazz зафиксирован `TLS raw=-32512`, что в локальном SDK mbedTLS соответствует `MBEDTLS_ERR_SSL_ALLOC_FAILED (-0x7F00)`, то есть ошибке TLS allocation; без MEMORY 7/8 нельзя установить, исчерпана ли общая heap или крупнейший непрерывный блок. Нет доказательств, что у **каждой** другой станции тот же TLS-отказ (например, plain HTTP может останавливаться на другом этапе).

Проверка `audioWorker` выявила **постоянную предварительную аллокацию 61 960 Б**: 32 768 Б ring + 29 192 Б libmad codec, даже между повторными TLS-попытками. В рабочем коде ring теперь резервируется **только после успешного HTTP/TLS open**, codec — перед созданием MP3-декодера (в offline mode без ненужного HTTP ring). `cleanup()` останавливает decoder, закрывает buffer/src и лишь затем освобождает оба внешних буфера; повторная TLS-попытка больше не обязана проходить с их постоянной аллокацией. При недостатке памяти на последующем выделении самого ring/codec исправление отказывается от декодирования и возвращается к штатной ошибке/retry, не меняя размеры ring/codec и не делая небезопасных вызовов к speaker. **Это гипотеза оптимизации, не доказанный hardware fix**: память должна хватить и после установления TLS. В `tests/test_tls_audio_memory_lifetime.py` добавлены 4 независимые source-contract проверки порядка аллокации и освобождения, 4/4 PASS. CA, hostname verification, TLS timeouts, prefill, MP3 watchdog, speaker ownership неизменны.
